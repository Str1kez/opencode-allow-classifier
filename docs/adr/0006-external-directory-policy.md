# `external_directory`: подтверждение для `cd` и внешних путей

**Status**: accepted

Плагин видит только shell-ресурсы. Смена каталога в них не попадает: OpenCode
2.2.4 разбирает `cd <путь>` до permission-хука и передаёт цель отдельным
действием `external_directory`. Туда же уходят чтение и редактирование вне
проекта. По умолчанию это действие разрешено, поэтому `cd /tmp` выполнялся
молча, а `cd /tmp; cat notes.txt` плагин проверял как `cat notes.txt` с cwd
проекта и выдавал `allow` — при том, что shell читал `/tmp/notes.txt`. Гард
`outside-cwd` такое не ловит: путь `notes.txt` лексически внутри cwd, а
`cd`-сегмента в ресурсах нет.

Это дыра в обещании «читать только внутри проекта», и закрыть её внутри
плагина нельзя: хук не получает ни полную команду, ни рабочий каталог
исполнения. Официальное руководство V2 предлагает для этого случая правило
`external_directory`, а не плагинный хук.

## Как проверено

OpenCode 2.2.4 в sandbox-контейнере, профиль `sandbox/config/opencode.jsonc`,
headless-прогон:

```sh
docker compose -f sandbox/compose.yaml run --rm -T agent \
  opencode run --standalone --model opencode/gpt-5.4-mini \
  "Run exactly one shell tool call: cd /tmp. Do not do anything else."
```

С правилом:

```text
! permission requested: external_directory (/tmp/*); auto-rejecting
✗ cd /tmp failed
```

Без правила (временно убранного из профиля) прогон `cd /tmp; pwd` выполняется
и печатает `/tmp`:

```text
$ cd /tmp; pwd
/tmp
```

По умолчанию действие разрешено; именно правило `ask` превращает `cd /tmp`
в подтверждение. Прогон без правила — разовая проверка дефолта, профиль в
репозитории остаётся с правилом.

## Решение

В политику добавляется правило:

```jsonc
{ "action": "external_directory", "resource": "*", "effect": "ask" }
```

Оно стоит после shell catch-all в чистой раскладке установщика,
`sandbox/config/opencode.jsonc`, README и `docs/permissions.md`. Порядок между
разными action не влияет на матчинг: правило срабатывает на `cd`-цели и на
внешние чтение/запись до запуска команды.

Установщик считает правило обязательным:

- `install` создаёт его в чистой раскладке и добавляет в существующий конфиг;
  если `external_directory *` уже есть с другим эффектом — конфликт, файл не
  меняется. Правило вставляется перед чужими `external_directory` правилами,
  чтобы конкретные allow/deny пользователя продолжали выигрывать по
  last-match;
- `inspect` предупреждает, если правила нет, эффект не `ask` или узкое
  `external_directory` правило стоит до catch-all и потому никогда не сработает;
- `rollback` удаляет правило, только если его добавил установщик; старые
  манифесты без этого поля читаются как «не добавлял».

## Рассмотренные альтернативы

- **Ловить `cd` внутри плагина.** Permission-хук получает только остаток
  команды: `cd /tmp; cat notes.txt` приходит как `["cat notes.txt"]` с cwd
  проекта. Ни `shell: cd *` с `deny`, ни разбор ресурсов это не меняют —
  проверки `cd` просто не вызывается. Хук `tool.execute.before` видит команду,
  но не может превратить уже принятый `allow` в `ask`, а блокировка через
  ошибку — это `deny`, а не подтверждение.
- **Оставить `cd` вне политики и записать в остаточные риски.** Тогда
  `cd /tmp; cat notes.txt` остаётся рабочим обходом `outside-cwd`: плагин
  разрешает чтение, которого не видит. Документация не делает дыру безопаснее.
- **Разрешить `external_directory` точечно по путям.** Список внешних
  каталогов всегда неполный, а `cd ..` и произвольный `/tmp` всё равно нужно
  закрывать. Catch-all `ask` — минимальное правило; узкие исключения оператор
  добавляет после него сам.
- **Понижать `external_directory` до `allow` для read-only команд.** Плагин не
  участвует в этом действии и не знает, какая команда за ним стоит. Любая
  попытка угадать по пути повторила бы allowlist без гардов.

## Последствия

- `cd /tmp` и `cd ..` спрашивают до выполнения; в headless-прогоне запрос
  отклоняется, команда не исполняется.
- `cd /tmp; cat notes.txt` не доходит до чтения: запрос на `cd`-цель
  отклоняется, `/tmp/notes.txt` остаётся непрочитанным.
- `cd sandbox; ls` проходит: цель внутри проекта, `external_directory` не
  срабатывает, а `ls` разрешает allowlist.
- Любое чтение и редактирование вне проекта тоже спрашивает. Это цена
  правила и возврат к поведению V1; ложный `ask` стоит одного нажатия.
- Если оператор удалит правило или переопределит его более поздним
  `external_directory` allow, обход через `cd` вернётся, а плагин этого не
  заметит. Поэтому `inspect` считает правило обязательным.
- Символические ссылки не разворачиваются: `ln -s /tmp link` внутри проекта,
  затем `cd link` проходят лексическую проверку — путь выглядит лежащим в
  проекте, хотя ведёт в `/tmp`. `ln` не входит в allowlist и спрашивает
  подтверждение, поэтому для обхода нужно явно разрешить `ln`; это остаточный
  риск, а не закрытая граница.
- Плагин и таблицы правил не меняются: решение принимает конфиг, аудит
  `external_directory` не пишет.
