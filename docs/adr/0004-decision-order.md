# Гард решает до allowlist

**Status**: accepted

До этого изменения `decide()` шёл по сегментам одним циклом: для каждого
сегмента сначала искал правило allowlist, и только если оно нашлось —
проверял гарды. Первый сегмент без совпадения выходил из цикла и уводил весь
вызов к классификатору. Из-за этого вердикт зависел от порядка сегментов:

```
cat ~/.ssh/id_rsa ; python3 -c 'print(1)'   -> guard:secret-ssh
python3 -c 'print(1)' ; cat ~/.ssh/id_rsa   -> default -> модель
```

Одного незнакомого слова хватало, чтобы выключить детерминированную защиту.
Модель при этом получала команду целиком и могла вернуть `allow` на чтение
`~/.ssh`. `docs/permissions.md` обещал обратное: «сработавший гард в
классификатор не уходит».

## Решение

Порядок фиксирован и каждый шаг проходит по всем сегментам, прежде чем
начнётся следующий:

1. hard-ask;
2. гард;
3. allowlist;
4. кэш и классификатор — только для того, что не прошло allowlist;
5. `ask` по умолчанию.

Гард больше не зависит от того, угадал ли allowlist программу. Сработавший
гард выносит `ask` на любом сегменте и останавливает решение: модель не
вызывается. В аудите такой вердикт получает `source: guard` и
`rule: guard:<имя>`.

`DECISION_SOURCES` — единственный источник словаря источников. Отчёт по
ask-кластерам читает `guard` как известный источник и относит его к рычагу
`allowlist-and-guards`, а не к `classifier-errors`.

Исторические записи с `source: allowlist` и `rule: guard:*` остаются
валидными. До смены порядка гард мог сработать только на сегменте, который уже
совпал с allowlist; отчёт читает обе подписи одинаково.

## Рассмотренные альтернативы

- **Оставить гард внутри цикла, но не выходить на первом несовпадении.**
  Меньше правок, но гард по-прежнему проверяется только после allowlist. Если
  ни один сегмент не совпал, гарды не проверяются вообще, и команда уходит к
  модели — та же дыра, просто без зависимости от порядка.
- **Проверять гард первым внутри каждого сегмента, цикл оставить.** Закрывает
  порядок, но не закрывает составной вызов: гард на втором сегменте не
  сработает, если первый уже отправил вызов к модели. Нужен именно проход по
  всем сегментам на каждом шаге.
- **Новый источник `guard` не вводить, писать `allowlist`.** Отчёт продолжил
  бы называть это allowlist-решением, хотя allowlist мог вообще не совпасть.
  Врать в аудите о том, кто принял решение, — ровно та проблема, из-за которой
  затевался порядок.
- **Сделать `guard` источником ошибки.** Гард — штатное детерминированное
  решение, а не сбой провайдера. В `classifier-errors` ему не место.

## Последствия

- `python3 -c 'print(1)' ; cat ~/.ssh/id_rsa` и обратный порядок дают
  одинаковый `ask` с `rule: guard:secret-ssh`.
- `cmd 2> err.log` спрашивает с `guard:redirect`, хотя `cmd` нет в allowlist.
- Часть сегодняшних модельных `allow` станет `ask`, если в команде есть сигнал
  гарда. Это осознанная цена: гард обязан выигрывать у модели.
- Счётчик вызовов модели на сработавшем гарде равен нулю — это проверяется
  тестом через хук плагина.
- Формат аудита не меняется, добавляется только новое значение `source`.
  Отчёт по старым и новым записям не падает и не считает `guard` неизвестным
  источником.
- Allowlist-рекомендация по записи с `source: guard` без совпадения с
  allowlist не выдаётся: гард срабатывает до allowlist, поэтому такая запись
  не доказывает, что команда read-only.
