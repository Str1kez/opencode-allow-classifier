# Разбор ask-аудита

Скилл читает месячные файлы `evaluate-YYYY-MM.jsonl`, отбирает `ask` за окно и
группирует их по нормализованной сигнатуре команды. На выходе — кластеры: сколько
раз спрашивали, распределение вероятности модели, источники, сработавшие правила,
число проектов и агентов, пример команды. Это отчёт, а не правка политики.

## Когда использовать

- Пользователь спрашивает, почему харнесс постоянно подтверждает одни и те же
  команды.
- Нужно понять, на чём копится `ask`, прежде чем менять allowlist, порог или
  hard-ask.
- Нужно сравнить окна, проекты или источники между собой.

## Команды

Запускай из корня репозитория, где лежит `.opencode`:

```sh
# окно по умолчанию — 30 дней
npm run report

# конкретное окно и машинный формат
npm run report -- --since=2026-09-01 --json
npm run report -- --since=7d

# разбор по источнику или правилу
npm run report -- --source=model --rule='guard:*'
npm run report -- --source=model,allowlist
npm run report -- --rule='guard:*' --rule='git-*'

# произвольный каталог аудита
npm run report -- --audit-dir /path/to/audit
```

`npm run report -- ...` передаёт флаги скрипту; без `--` npm съест их. Для чистого
JSON без баннера npm используй `npm run --silent report -- ...`. Прямой запуск:

```sh
node .opencode/skills/allow-classifier-analyze/scripts/cli.ts --since=30d
```

## Опции

| Опция | Значение |
|---|---|
| `--since` | `YYYY-MM-DD` или `<n>d`; по умолчанию `30d`. `<n>d` — с UTC-полуночи дня, отстоящего на n дней назад; `0d` — с сегодняшней UTC-полуночи. |
| `--config` | Конфиг, из которого берутся `audit_dir` и `threshold`. Отсутствие файла или ошибка разбора — код `1`. |
| `--audit-dir` | Каталог аудита. Побеждает `audit_dir` из конфига; `threshold` по-прежнему берётся из конфига, иначе дефолт `0.9`. |
| `--source` | Точное имя источника (`model`, `allowlist`, `hard-ask`, `default`, `cache`, `error`). Повторяемая или через запятую. |
| `--rule` | Глоб с `*` по имени правила. Повторяемая. Матчится любое правило из строки через запятую. |
| `--json` | Стабильный JSON вместо текста. |
| `--include-sandbox` | Читать аудит внутри `<repo>/sandbox`. По умолчанию он исключён. |

## Откуда берётся каталог аудита

1. `--audit-dir`, если задан.
2. `audit_dir` из записи плагина в конфиге: `--config`, иначе ближайший
   `opencode.jsonc`/`opencode.json` от текущего каталога вверх, иначе глобальный
   `$XDG_CONFIG_HOME/opencode` / `~/.config/opencode`.
3. `$XDG_STATE_HOME/opencode`, иначе `~/.local/state/opencode`.

Относительный `audit_dir` считается от текущего каталога — так же, как его увидит
плагин. Если конфиг битый, скрипт пишет предупреждение и идёт дальше по цепочке;
явный `--config` с ошибкой останавливает отчёт.

## Сигнатура и кластер

- `resources` склеиваются разделителем ` ; `.
- Сигнатура — ключ кластера: whitespace схлопывается, длинные hex-токены
  (8+ символов, есть хотя бы одна буква) заменяются на `<hex>`, затем числовые
  последовательности — на `<n>`.
- Пустой набор команд — `<empty>`.
- Пример команды — лексикографически наименьшая исходная команда в кластере,
  без подстановки `<n>`/`<hex>` и без схлопывания пробелов; поэтому отчёт не
  зависит от порядка строк в файле. Перевод строки в примере остаётся видимым:
  спрятанная вторая команда не должна выглядеть безобидным one-liner.
- `activeSyntax` — `true`, если хотя бы у одной записи кластера в сырых ресурсах
  остался активный shell-синтаксис после вычета кавычек: `;`, `&`, `|`, перевод
  строки, подстановка, глобы. Флаг считается по всему кластеру, а не по
  показанному примеру.

Кластеры сортируются по числу вхождений, затем по сигнатуре. Вероятность считается
только по записям, где она есть; у hard-ask и гардов её нет (`probability: none`).
Число агентов считается по непустым именам.

## Рычаги

Каждый кластер попадает ровно в один рычаг. Если источники смешаны, приоритет
такой:

1. `error` → `classifier-errors`. Ошибка провайдера, модели или таймаута — это
   сбой, а не свидетельство о политике; в рекомендации по allowlist она не
   попадает никогда.
2. `hard-ask` → `hard-ask`. Детерминированное правило не зависит от порога и
   allowlist, поэтому оно и есть рычаг.
3. `allowlist` или `default` → `allowlist-and-guards`.
4. `model` или `cache` → `model-and-threshold`.

Неизвестный источник считается ошибкой и уходит в `classifier-errors`.

Рекомендация появляется только при трёх и более вхождениях. Кластер с одним или
двумя вхождениями — наблюдение (`observations`), без рекомендации: это шум, а не
паттерн.

## Рекомендации

Порядок по безопасности, сверху вниз:

1. `allowlist-expansion` — расширение allowlist для существующей read-only
   команды.
2. `hard-ask-exception` — узкое исключение из hard-ask.
3. `threshold-lowering` — понижение порога.

Расширение allowlist предлагается только тогда, когда команда действительно
read-only: форма не совпала с allowlist или сработал гард-ложное-срабатывание
(`guard:shell-metacharacter`). Форма с активным shell-синтаксисом — пайпом, `;`,
переводом строки или подстановкой — read-only не считается. Если `activeSyntax`
у кластера включён, рекомендации нет ни по одному рычагу: allowlist, исключение
из hard-ask и снижение порога одинаково пропустили бы спрятанную вторую команду.
В заметке печатается, что команда содержит активный shell-синтаксис, а гард или
правило остаётся. Вокруг `guard:secret-env`, `guard:outside-cwd`,
`guard:redirect` и других защитных гардов расширения нет: там рекомендация —
оставить гард и не менять права. Это явно печатается в заметке кластера.

Read-only не значит безобидный: команда может напечатать секреты. Поэтому
`kubectl get secrets -o yaml`, `kubectl describe`, `kubectl logs` и
`docker logs/inspect` не считаются безопасной формой, а риск каждой
allowlist-рекомендации напоминает, что добавлять нужно только ту форму, вывод
которой допустимо показать.

Исключение из hard-ask обязано быть узким: точная форма команды, названный риск
ослабления hard deny и причина. Для `git push`, `rm` вне cwd, `sudo`, установок
и миграций исключение не предлагается вообще; если hard-ask законен,
рекомендация — оставить. Понижение порога берётся только из `model`/`cache`:
в рекомендации перечислены новые allow-формы и риск ложных allow, а порог
сравнивается с эффективным значением из конфига (по умолчанию `0.9`).

Каждая рекомендация содержит рычаг, сигнатуру, число вхождений, новые allow,
риск и обоснование. Рекомендации сортируются по типу (allowlist → hard-ask →
порог), затем по вхождениям и сигнатуре.

Deny-правила вне области: отчёт не предлагает добавить, убрать или ужесточить
deny. Это граница, а не тюнинг. Ошибки классификатора идут отдельной секцией с
рекомендацией починить провайдера, модель или таймаут — без советов по allowlist.

## Что печатается

Текст: шапка с каталогом аудита, конфигом, окном, признаком песочницы, числом
файлов, отобранных записей и пропущенных строк, фильтрами и числом кластеров.
Дальше — блоки кластеров с полями `signature`, `occurrences`, `probability`,
`sources`, `rules`, `projects`, `agents`, `example`, `activeSyntax`, затем секции
рычагов, рекомендации, наблюдения и ошибки классификатора. Пустая секция печатает
`none`, чтобы форма вывода не менялась.

`--json` печатает ту же информацию стабильными ключами: к #13-полям добавлены
`levers`, `recommendations`, `observations`, `classifierErrors` в конец объекта.
В отчёте нет времени генерации: повторный прогон на тех же данных даёт байт в
байт тот же вывод.

Фильтры сужают только выборку. Шапка и формат блоков не меняются, поэтому отчёт
можно резать по частям и сравнивать.

## Приватность и границы

- Аудит содержит `task` — текст последнего сообщения пользователя, а также `cwd`,
  идентификаторы сессий и имена агентов. Не выкладывай JSONL целиком в чат и не
  копируй примеры с чувствительными путями.
- Отчёт по умолчанию идёт в stdout. Файл создаётся только по явной просьбе
  пользователя; предупреди, что в аудите лежит текст его сообщений.
- Скрипт read-only: ничего не пишет, не создаёт каталогов, не правит конфиг и не
  меняет политику. Применение выводов — отдельная команда пользователя.
- Аудит песочницы — тестовые данные, а не поведение. Без `--include-sandbox` он
  не читается.
- Не запускай реальный OpenCode с плагином на хосте: живые прогоны — только в
  `sandbox/`.
- Отчёт остаётся read-only и после рекомендаций: он не пишет файлы, не правит
  allowlist, порог или deny и не применяет свои же советы. Применение — отдельное
  решение и команда пользователя.
